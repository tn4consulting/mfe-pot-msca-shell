# mfe-pot-msca-shell

## What this is

The **MSCA host app** for the mfe-pot Government of Canada MFE proof-of-technology: the branded MSCA ("My Service Canada Account") app frame — GC header/footer, language switcher, a real authorization-code + PKCE sign-in flow against `mock-idp`, runtime federation manifest reader. It loads `mfe-pot-job-bank-mfe`, `mfe-pot-employment-insurance-mfe`, `mfe-pot-dashboard-mfe`, and `mfe-pot-life-events-mfe` dynamically at runtime as federated remotes (`-mfe`-suffixed repo/federation-identity naming, disambiguating them from either host app's own front-door name — see the meta repo's `../CLAUDE.md`); none of their source is compiled in here. It's one of **two** host apps in the family — `mfe-pot-job-bank-shell` is the other, a minimal second host that composes only the job-bank remote, proving the same federation pattern generalizes beyond a single shell.

## What's in this repo

- `apps/msca-shell` — the only app; no co-located BFF (a pure federation host). No `libs/` — msca-shell has no feature code of its own beyond the app frame and login/callback pages.
- `charts/msca-shell` — this app's Helm chart, depending only on the platform repo's `mfe-frontend-lib` library chart (no backend, so `mfe-backend-lib` isn't used) plus a hand-written `templates/ingress.yaml`.
- `apps/msca-shell/Dockerfile` — nginx-served static build; see the platform repo's CLAUDE.md ("Hosting: Kubernetes + Helm") for the shape and the Docker-build gotchas (npm auth secret mount, the `nx` postinstall hang fix) that apply here too.

Depends on published packages from GitHub Packages: `@tn4consulting/shared-auth`, `shared-content-client`, `shared-federation-config`, `shared-federation-runtime`, `shared-i18n`, `shared-runtime-config`, `shared-ui-scds-core` (pinned in `package.json`; keep in sync with `platform-versions.json` in `mfe-pot-platform`). `shared-content-client` powers `LifeEventsHubPage.tsx`'s own CMS-driven hub-tile content (`life-events.<id>.hub-tile` keys, `content-client.ts`) — this repo does render CMS-driven content, just narrower than a full-page-content app (only the hub page). GCDS has been removed from the family entirely (see the platform repo's CLAUDE.md) — msca-shell renders `@tn4consulting/shared-ui-scds-core`'s custom elements directly (its app-frame components: `scds-header`/`scds-sidebar`/`scds-footer`/etc.), no wrapper package.

## Repo-specific things worth knowing

- **`apps/msca-shell/src/main.tsx` cannot import any `@tn4consulting/shared-*` package**, including ones this repo otherwise depends on (`shared-remote-registry` isn't even a dependency here for this reason) — `main.tsx` runs before Native Federation's import-map/shared scope exists, and any bare-specifier import from it resolves through that not-yet-ready map. `main.tsx` inlines its own small `{ ...devDefaults, ...window.__mfePotEnv }` runtime-config merge and its own Strapi-first-with-fallback federation-manifest resolution instead of using `shared-remote-registry`/`shared-runtime-config` directly. `apps/msca-shell/src/runtime-config.ts` is a *separate*, second runtime-config module that genuinely does import `shared-runtime-config` — safe because it's only imported from lazy-loaded route components (`LoginPage`, `AuthCallbackPage`), which run after Native Federation's shared scope already exists. `main.tsx`'s own ambient `Window.__mfePotEnv` type declaration has to match `shared-runtime-config`'s exactly, since TypeScript requires identical types across merged ambient declarations of the same global once both files are in the same program. See the platform repo's CLAUDE.md for the fuller explanation (same root cause documented there for every app).
- **Runtime config shape in `main.tsx` is `{ strapiBaseUrl, remotes }`** — `remotes` is a `Record<name, remoteEntryUrl>`, the federation directory. `resolveFederationManifest()` tries Strapi first (3s timeout), falling back to `runtimeConfig.remotes` if unset. `runtime-config.ts`'s separate shape is just `{ mockIdpBaseUrl }` — the PKCE flow's own single dependency.
- **The real PKCE sign-in flow lives entirely in this repo**: `auth-flight.ts` (PKCE `generateRandomToken`/`computePkceChallenge` — S256 with a `plain` fallback for non-secure-context deployments — plus `storeAuthFlight`/`consumeAuthFlight`), `LoginPage.tsx` (builds the PKCE params and full-page-redirects to `mock-idp`'s `/authorize`, `CLIENT_ID = 'mfe-pot-msca-shell'`), and `AuthCallbackPage.tsx` (reads `?code&state`, validates it against the stored flight, `POST`s `mock-idp`'s `/token`, calls `storeSession()`). `mock-idp`'s `ALLOWED_REDIRECT_URI_ORIGINS` must include this app's own Ingress origin alongside `mfe-pot-job-bank-shell`'s — see the platform repo's CLAUDE.md "Security: defense in depth" section for the cross-repo picture (what `mock-idp` and each BFF do with the resulting JWT).
- **This is one of the two app repos where SCDS's app-frame components live** (the other is `mfe-pot-job-bank-shell`, minus the sidebar): `apps/msca-shell/src/app/scds-elements.d.ts` types the `scds-header`/`scds-sidebar`/`scds-footer`/etc. custom elements msca-shell renders directly via JSX — remotes render content only, never their own header/footer/nav (per the platform repo's SCDS section). This includes the full sidebar nav (category group + account/utility group, collapsible via a hamburger toggle at narrow viewports) — it lives here rather than in any one remote because it needs to appear on every route across all 4 remotes, the same reason header/footer are msca-shell-owned. `@tn4consulting/shared-ui-scds-core` must stay a federation-shared singleton in `federation.config.mjs` (via `shared-federation-config/react`'s `sharedUiScdsCoreFederationDependency`), or a version mismatch across remotes would silently skew toward whichever bundle's `customElements.define()` call happened to run first — no crash, since plain custom elements don't collide on double-registration.
- **`apps/msca-shell/src/app/routes.tsx` is where msca-shell provides the cross-remote widget registry** — a single `WIDGET_REGISTRY` constant (keyed by widget id: `payment-history`, `job-applications`, `ei-reporting-status`) wrapped in one `<WidgetRegistryContext.Provider>` around the whole route tree (`@tn4consulting/shared-federation-runtime@2.0.0+`'s generic keyed-widget-loader mechanism, replacing the old one-Context-per-widget-type wiring) — this is the one place in the family that actually wires up the host-mediated widget-composition pattern the platform repo's CLAUDE.md describes. `mfe-pot-job-bank-shell`'s equivalent file has none of this wiring — it only ever mounts job-bank's own `./Component`, never a cross-remote widget. If a cross-remote widget ever silently shows its "unavailable" fallback with no console error even though its BFF/remote is genuinely reachable, check here first — `WIDGET_REGISTRY` might be missing an entry for that widget id, or `WidgetRegistryContext.Provider` might not be wrapping the route that needs it.
- **A real, hard-won gotcha in `apps/msca-shell/build/build.mjs`/`serve.mjs`**: the `external` array in the plain `esbuild.build()`/`.context()` call for `main.tsx`'s own bundle must list every package this bundle needs Context-identity-sharing with, not just `react`/`react-dom`/`react-dom/client`. Confirmed the hard way (a real dashboard route, job-bank and employment-insurance both running): omitting `@tn4consulting/shared-federation-runtime` silently inlined a second, disconnected copy of the widget-loader Context objects into this bundle, so `routes.tsx`'s Context providers wrote into a copy no consuming remote's `useContext` call ever actually read from — no error, no console output, just every cross-remote widget rendering its "unavailable" fallback forever, indistinguishable from a genuinely unreachable remote. The federation build (`runEsBuildBuilder`, the other half of `build.mjs`) already produces the correct shared chunk; this `external` entry is what makes `main.tsx`'s own bundle resolve through it instead of bundling a second copy. See the platform repo's CLAUDE.md "Federation" section for the fuller writeup.
- **CI** (`.github/workflows/ci.yml`): lint/test/build, then builds the image, spins up an ephemeral `kind` cluster, `helm install`s this chart, and curls the Ingress-routed hostname to confirm it serves — the automated version of the kind validation described above. Checks out `mfe-pot-platform` as a sibling directory (public repo, no extra secret needed) so the chart's `file://` library-chart dependency resolves the same way it does in local dev. See `README.md` for local install/serve/build/Docker/Helm instructions.
- **`LifeEventsHubPage.tsx` (`/life-events`) is shell-owned, not a remote** — two `scds-card` grids: one entry-point tile per life event (`href="/life-events/<id>"`, title/description from `content-client.ts`'s new CMS-driven hub-tile keys, `life-events.<id>.hub-tile`) and one for the conventional benefit-administration destinations (`/dashboard`, `/job-bank`, `/employment-insurance`). Doesn't replace `/dashboard` as the post-login landing page — reached via its own sidebar nav entry (`nav.lifeEvents`) instead. `/life-events/:lifeEventId` mounts `mfe-pot-life-events-mfe`'s single remote parametrically — see that repo's own CLAUDE.md for the multi-life-event kit this composes with, and `RemoteRouteHost`'s `props` (added in `shared-federation-runtime@2.0.0`) for how the route param crosses the federation boundary as a plain prop rather than a `useParams()` call inside the remote.
